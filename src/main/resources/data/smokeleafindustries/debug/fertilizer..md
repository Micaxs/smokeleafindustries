# SmokeleafIndustries — Recipe & Nutrient Audit (Dev Cheatsheet)

Generated by an audit pass over the current `rework` branch. Everything below was verified
directly against the live source (item registrations, recipe JSON, and the actual fertilizer/NPK
code paths) — not copied from an older cheatsheet. File:line references are given so findings can
be re-checked quickly.

---

## 1. Recipe Audit

### 1.1 Result: no broken recipes found

Checked all 63 static recipe files under `data/smokeleafindustries/recipe/` for:

- **JSON validity** — all parse cleanly.
- **Dangling item/block references** — every `"item"` / result `"id"` / `"item"` reference
  resolves to either a registered `smokeleafindustries:` item/block or a real vanilla item.
  (Two initial hits — `smokeleafindustries:hash_oil_bucket` in
  `recipe/generator/hash_oil_to_energy.json` and `hemp_oil_to_energy.json` — turned out to be a
  false alarm in the audit script, not a real bug: bucket items are registered in
  `ModFluids.java` rather than `ModItems.java`, so the first pass just hadn't collected them.)
- **Recipe id collisions** — no static recipe shares a path with a datagen'd one, and no two
  static files collide with each other.
- **Recipe "type" values** — every custom `"type"` (e.g. `smokeleafindustries:sequencer`,
  `smokeleafindustries:liquifier`, `smokeleafindustries:gummy_machine`, ...) matches a serializer
  actually registered in `ModRecipes.java`.
- **Required fields per custom recipe codec** — cross-checked every static JSON's type against
  that recipe class's `MapCodec` (non-optional `fieldOf(...)` entries) in
  `src/main/java/net/micaxs/smokeleaf/recipe/`. All required fields are present in all files.

**Conclusion: no broken recipes.**

### 1.2 Missing recipes

162 registered items/blocks were checked against every recipe result (static + datagen'd) in the
mod. 42 have no recipe — of those, 17 are intentionally recipe-less (raw crop drops, bucket-fill
items, loot/trade-only items, the shared pipe block placed via its item variants, etc.) and are
listed here only for completeness:

| Item | Why it has no recipe (intentional) |
|---|---|
| `hemp_leaf`, `hemp_seeds`, `bud`, `tobacco_seeds`, `tobacco_leaves` | raw crop drops |
| `hemp_crop`, `tobacco_crop`, `unidentified_weed_crop` | crop blocks, placed by planting a seed |
| `hash_oil_bucket`, `hash_oil_sludge_bucket`, `unidentified_mixture_bucket` | vanilla bucket-fill mechanic |
| `pipe` | placed via the Item/Fluid/Energy Pipe items, never obtained directly |
| `cat_urine_bottle` | obtained by right-clicking a cat with a glass bottle |
| `dual_arc_lamp` | villager trade + (this session) archaeology/trial chamber loot |
| `empty_tincture`, `hash_oil_tincture` | villager trade + fill-on-Liquifier interaction |
| `white_widow_bag` | trial chamber loot only (intentional, no recipe) |

**The other 25 are a genuine gap**, and are worth a decision: every per-strain Gummy item
registered in `ModItems.java` (`afghani_gummy`, `ak47_gummy`, `amnesia_haze_gummy`, ...
`white_widow_gummy` — the full 25-strain set) is **unreachable**. They're registered and have item
models, but:

- No recipe produces them (the generic `GENERIC_GUMMY` item — plain `gummy` — is what the Gummy
  Machine actually outputs now, tinted per-strain via `StrainData` at runtime).
- No loot table or villager trade grants them either.

These are leftovers from before the "Remove legacy per-strain items/blocks, fully migrate to
generic strain system" migration (see git log) and are pure dead weight now. Recommend either
deleting the 25 registrations (and their item models/lang entries) or, if they're meant to stay as
a creative-only/legacy curiosity, saying so explicitly somewhere — right now they just look like a
missing recipe.

## 2. Nutrient (N-P-K) System Audit

### 2.1 How "perfect" actually works, and the bug that blocks it

The mod computes a "perfect" bonus (3x buds, and `computeWithNutrients` doubles THC/CBD) only when
the crop's current N/P/K **exactly** equals a target N/P/K (`dn == 0 && dp == 0 && dk == 0`).
Within `NPK_TOLERANCE` (3) of the target still gives a partial bonus; more than 3 off on any axis
gives none.

There are **two separate, differently-wired copies of this logic**, and only one of them works:

- **`GrowPotBlockEntity`** (`block/entity/GrowPotBlockEntity.java:516-588`) — when a named strain
  is planted (`setCustomStrain`, line 600), it explicitly resets N/P/K to 0 and uses the **strain's
  own `StrainData.nitrogen()/phosphorus()/potassium()`** as the target
  (`hasCustomStrain() && customStrain != null` branch). This is correct and **works today** for all
  25 preset strains.
- **`BaseWeedCropBlockEntity`** (used for crops planted on farmland via `BaseWeedCropBlock` /
  `UnidentifiedWeedCropBlock`) — `isValidNutrientsLevels()`, `getBudCount()`, and
  `computeWithNutrients()` (lines 101-174) **never look at the planted strain's `StrainData` at
  all**. They only ever call `Config.getNutrientTargetFor(getCropId())`, where `getCropId()`
  (private, line 96) returns the **block's own registry id** —
  `smokeleafindustries:unidentified_weed_crop` (or `hemp_crop`/`tobacco_crop`) for literally every
  strain, since there's only one generic crop block now.

  `Config.java`'s `PLANT_NUTRIENTS` default list (lines 61-91) is keyed by the **old per-strain
  crop block ids** — `white_widow_crop`, `bubble_kush_crop`, etc. — which don't exist anymore
  post-migration. So `Config.getNutrientTargetFor("smokeleafindustries:unidentified_weed_crop")`
  **always returns empty**, and every one of those three methods silently falls back to "no bonus,
  ever" (`return true` / `return 1` / `return base` unchanged).

**Practical effect: fertilizing a crop planted on farmland currently has zero effect on final
yield or potency, for any strain. The mechanic only works when the strain is grown in a Grow Pot.**

Fixing this properly means giving `BaseWeedCropBlockEntity` the same "read the target from the
planted seed's `StrainData` first, fall back to `Config` only for un-stained generic crops" logic
`GrowPotBlockEntity` already has — `BaseWeedCropBlockEntity` doesn't currently store or have access
to the planted item's `StrainData` at all, so that'd need adding.

### 2.2 Stale data in `Config.java`

Even ignoring the id-mismatch bug, `Config.java`'s hardcoded defaults have drifted from the live
`StrainRegistry.java` presets for 2 of the 25 strains (the other 23 still match exactly):

| Strain | `StrainRegistry.java` (live) | `Config.java` default (stale) |
|---|---|---|
| White Widow | N9 P6 K11 | N11 P8 K10 |
| Bubble Kush | N10 P8 K16 | N12 P10 K18 |

If/when the lookup bug above gets fixed, these two either need reconciling or the `Config` fallback
path should be removed in favor of always reading `StrainData` directly, since that's the only
copy actually being kept up to date.

### 2.3 Answering "which strains can't currently be made perfect"

**All 25 preset strains *can* be made perfect — but only when grown in a Grow Pot.** The math
checks out for every one of them (§2.5). Grown on farmland, **none** of them can currently be made
perfect, regardless of strain — that's the wiring bug in §2.1, not a nutrient-math limitation.
